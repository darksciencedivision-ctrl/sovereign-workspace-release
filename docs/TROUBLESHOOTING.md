# Troubleshooting

**Version 1.0.0-rc.1** · EPC-01 P4-9

Symptoms that have actually been observed, with what caused them. Where a cause is known to be
an open defect it says so and names the tracking id.

---

## SOVEREIGN reports models missing, or nothing will start

**Check `OLLAMA_MODELS` first.** It is the most common cause and the least obvious.

```powershell
[Environment]::GetEnvironmentVariable('OLLAMA_MODELS','User')
Invoke-RestMethod http://127.0.0.1:11434/api/tags | Select-Object -ExpandProperty models |
  Measure-Object | Select-Object Count
```

If the variable names a directory with no `manifests\` folder, Ollama serves an empty library
and every configured model reports missing. Point it at your real library, or unset it to use
Ollama's default.

**A running Ollama service does not pick this up until it is restarted.** Changing the
variable and re-probing without a restart shows the old, wrong answer — this has fooled people
before.

## Debate reports `degraded` but `missing_models` is empty

Working as designed. A seat's model is installed but sits **above the 8B nameplate ceiling**,
so it cannot take its turn. Reporting `ready` would be a silent absence wearing a green badge.

The `seats` array names the model and carries a `ceiling_reason`. Either configure a seat
within the ceiling or have the operator rule on the ceiling — it is not a fault to be worked
around in configuration.

## `llama.cpp` shows "Runtime not installed"

Correct, not an error. It ships as an **optional** adapter with a placeholder root, because no
llama.cpp runtime is bundled. The card names the path it expects. Install a runtime there, or
ignore the card.

## `pytest` at the repository root used to crash — if it still does

It should not. `modules/sow/conftest.py` once raised `ValueError` on any test collected
outside its own module, which pytest turns into `INTERNALERROR` and which aborted the entire
run, including on an extracted archive. Fixed under P1-4.

If you see `INTERNALERROR` during collection again, that guard has regressed. The test that
holds it is `shell/tests/test_whole_product_collection.py`.

---

## Tests pass per module but fail in the whole-product run

**Believe the whole-product run.** Twenty such failures have been found and fixed, and they
were real every time. Two causes account for all of them:

1. **A subprocess with the wrong `sys.path`.** Several suites spawn a child process
   deliberately. Run from the module directory, the child inherits a cwd that happens to be
   the module root and its imports resolve by accident. Run from the repository root, they do
   not. The root `conftest.py` exports `PYTHONPATH` for exactly this.

2. **A default of `root="."`.** Any function resolving a path against the *caller's* working
   directory is right by accident from one place and wrong from another. Derive it from
   `__file__`.

If you add a module, check both before assuming a new failure is flaky.

## The release manifest check fails on `shell/BUILD-MANIFEST.txt`

That file is regenerated by the shell test suite and carries a `# utc:` line, so its
whole-file hash changes on every run while its content does not. It is declared in
`RELEASE-MANIFEST.json` under `generated_artifacts` and hashed **without** its generation
stamp.

If it fails, the *content* genuinely changed — usually because files were added to `shell/`.
Re-pin it using the content hash, not the whole-file hash.

## The package boundary gate reports tens of thousands of violations

You are scanning the working tree. Use the archive:

```powershell
py -3.12 tools\release\package_boundary_gate.py --from-commit HEAD
```

A working tree holds `.venv`, `node_modules`, `.pytest_cache` and build output. None of it
reaches a recipient, and none of it is a packaging defect.

## Uninstall refuses to run

```
Refusing uninstall because exact installed path set changed
```

**Known defect, P0-5.** Uninstall compares the whole install tree against its manifest and
refuses if anything was added — and the product's own runtime state is an addition. It
therefore works only on an installation that has never been used.

Until it is fixed: copy out anything you want to keep (see the state table in
`docs/OPERATIONS.md`), then delete the install directory by hand.

---

## Upgrading

There is no upgrade path in this release (**P1-1**). `install.ps1` refuses a non-empty
destination by design, and uninstall is blocked by P0-5, so there is no supported route from
one version to the next.

If you must move: back up the state directories, install the new version to a **different**
destination, and copy state across by hand. Nothing validates that the state formats match —
this is a release candidate and they may not.

## The Electron app will not start

Check the binary is actually there:

```powershell
Test-Path "C:\SovereignWorkspace\modules\sow\apps\desktop\node_modules\electron\dist\electron.exe"
```

If it is missing, the install did not complete its provisioning step. Re-run the installer to
a clean destination — `install_sow.py` fetches Electron as a hash-verified zip and logs each
step, so its log will say where it stopped.

Do **not** run `npm install` by hand to fix it. That lets Electron's postinstall download the
binary with no hash verification, which is exactly what `docs/ADR-005-...` exists to prevent.

## Reporting something not listed here

There is no ticketing system and the product reports nothing on its own. Include:

1. Workspace version and the seal commit from `RELEASE-MANIFEST.json`.
2. `verify_install.ps1` output.
3. The console output of the service that misbehaved — capture it, because nothing else keeps it.
4. What you expected, what happened, whether it reproduces.

See `docs/SUPPORT-POLICY.md` for what is and is not promised in return.
