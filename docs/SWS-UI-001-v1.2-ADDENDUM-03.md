## 1. Why merge, and why it is safe

`docs/CP-02-CONFLICT-AUDIT.md` found four overlapping file areas between the packages — `modules/sow/adapters/**`, `modules/sow/control_plane/**`, `shell/src` + `shell/static`, and `evidence/GATE-LEDGER.json` — and concluded: *run them back to back, never side by side.*

**The hazard in that finding is concurrency, not adjacency.** Two agents editing one Protocol definition from opposite directions corrupts it; one agent doing CP-01's edit and then CP-02's edit does not. A merged directive executed by a single builder in a single session has exactly one writer, which is a stronger guarantee than two sequential sessions — there is no window between them in which a third party can move the tree.

The merge is therefore permitted **on one condition, absolutely**: the goal ladder is strictly ordered and executed in order. Every Package-A goal (G1–G63) is TRUE before any Package-B goal (G68 onward) is acted on. Band 16 populates the registry Band 7 creates; Band 14 widens a Protocol Band 6 leaves in its narrow shape. Out of order, that is the collision the audit warned about, inside one session instead of across two.

**The merge also buys real dedup, which CP-M1 §2.1 takes.** The registry is authored artifact-aware and context-aware in one pass, deleting an entire migration risk class. The failure vocabulary is defined once and reused. The main UI is laid out once for both panels. The protected roots are hashed twice rather than four times — roughly thirty minutes of sov-1 alone. One fs-watch window; one report. Concatenating the two packages would have bought none of that.
