## 2. Workstream 1 — lifecycle and recovery

### 1.1 Upgrade (L1)

`tools/release/upgrade.ps1` is now a journalled transaction whose controller is **staged outside
both the outgoing and the incoming installation**, so it survives replacing the directory it was
started from. Six phases: `resolve` (path validation, overlap/root/device refusal), `verify`
(sidecar hash *and* archive structure; an artifact stored under the destination is copied to the
transaction root first, so displacing the destination cannot lose it), `preflight` (interpreters,
disk space, write permission, quiescence of the outgoing install, a same-volume rollback route,
state-schema compatibility — everything that could fail *after* the move, checked *before* it),
`snapshot`, `cutover`, `postcheck`.

- A cutover or postcheck failure rolls back automatically, preserves the failed incoming tree as
  evidence, and prints **no success line**.
- A rollback that itself fails prints the exact surviving paths and the recovery steps, exit 5.
- Child scripts run as child processes, so the exit codes the guards read are real. `&` on a
  `.ps1` never sets `$LASTEXITCODE`; that was L1's second half and it is closed here and in
  `run_ci.ps1`.
- Exit codes are a contract: 0 upgraded, 2 refused before any change, 3 failed before cutover,
  4 failed and rolled back, 5 rollback failed.

**A deliberate design decision, stated rather than hidden.** The directive asks that the incoming
install be prepared in isolation and warns that a working staging install is not proof its
relocated form works. That warning is decisive here: this product builds three CPython venvs, and
a venv records its absolute path in `pyvenv.cfg` and in every `Scripts\*.exe` shim, so a venv
prepared at a staging path and moved is broken. The resolution is therefore **not to relocate a
prepared install at all** — structure and dependencies are validated in isolation, and the one
path-bound step happens once, at the final path, with a tested rollback behind it.

**Evidence:** `shell/tests/test_upgrade_transaction.py` — 20 cases, all passing: invocation from
inside the outgoing install (the recorded L1 reproduction), external invocation, spaces in paths,
artifact inside the outgoing install, occupied and overlapping rollback locations, an overlapping
transaction root, a filesystem-root destination, a missing interpreter found at preflight, a
malformed archive, an escaping archive entry, a tampered archive, a state-schema change requiring
acknowledgement, and injected failures at preparation, cutover, postcheck and rollback, plus
journal durability and the staged-controller property.

### 1.2 Backup and restore (L2)

The snapshot contract is now **offline, and proven rather than assumed**. `backup_state.ps1`
opens each file denying other writers; if anything is being written it refuses and names the
files. `-AllowNonQuiescent` captures anyway and labels the inventory
`online-uncoordinated (NOT a consistent snapshot)` — the flag removes the refusal, not the
inconsistency, and the documentation says so.

- Enumeration is `-Force`: hidden and system entries are captured, and directory entries are
  stored so a required-but-empty directory survives.
- Reparse points are **refused**, not silently followed or dropped.
- Operator state is stored under a `state/` prefix with the inventory at the archive root, so a
  user file named `STATE-BACKUP-INVENTORY.json` round-trips like any other. The previous version
  wrote its inventory into, and deleted it from, the operator's **live state root**.
- The inventory records path, length, SHA-256 and attributes for every entry, plus the product
  version and the snapshot method. A file count is not an inventory.
- The archive is built under a `.partial` name, reopened and verified entry-by-entry, and only
  then moved to its final name. A capture that does not verify never occupies the
  successful-backup name.
- Restore stages, validates every archive path (escape, absolute, duplicate, case-collision),
  checks the entry set against the inventory, re-hashes every extracted file, and only then
  displaces the existing state — which is moved aside, never deleted. An inventory-less archive
  is **refused** unless explicitly opted into, and is then labelled `NOT VERIFIED`.
- Integrity is distinguished from authenticity in the code, the docs and the output: the sidecar
  proves the bytes, and authenticates no publisher. No signing infrastructure is claimed.

**Evidence:** `shell/tests/test_state_snapshot_contract.py` (10 cases) plus the pre-existing
`test_state_backup_round_trip.py` (5 cases) — 15 passing, covering the recorded hidden-file
reproduction, Unicode and spaces, empty files and directories, a pre-existing inventory-named
user file, a short archive, a tampered archive, an escaping entry, a legacy archive, and refusal
to overwrite. The original L2 reproduction script now runs clean end to end.

### 1.3 Module lifecycle (L3)

Every start/stop/cancel/restart is an **operation with an identity**. Admission and the
`STARTING` transition happen together under the runner's lock, so two simultaneous requests
cannot both spawn; the lock is never held across a probe, a spawn or a process stop, so a
90-second SOW readiness wait cannot block the shell.

- Named cancellation checkpoints — `pre_spawn`, `post_spawn`, `post_readiness`, `post_identity` —
  drop any result whose operation has been superseded.
- A superseded start stops **only the process it created**, never whatever now answers to the
  reusable module id.
- `poll()` no longer touches `STARTING`, and no longer erases a diagnostic failure because a port
  went free. `EXTERNAL` and `PORT_OCCUPIED_UNRECOGNIZED` are observations about the port and
  still clear; `HEALTH_CHECK_FAILED` and its siblings are this shell's diagnosis of its own last
  start and survive until a new operation.
- Deadlines and the start rate limit use monotonic time. `port_owner_pid`'s subprocess is
  bounded, and an unreadable table is reported as unknown rather than as free.

**Evidence:** `shell/tests/test_lifecycle_serialization.py` — 8 cases using events, not sleeps,
all passing, including the recorded STOPPED-to-stale-READY reproduction; plus the pre-existing
16-case `test_states.py` still green.

## 3. Workstream 2 — release gates

Both failing gates pass on the candidate, and the repairs were made at the source of the drift
rather than by refreshing an expectation. Full record and negative controls:
`02-release/CANDIDATE.md`.

**R1.** The actual consumers were traced rather than a roster chosen. `SYSTEM_MANIFEST MODELS`
is the only source the shipped service reads for role assignment — `_quick_executor` and
`_deep_executor_from_manifest` both resolve from it, and `SemanticDeepExecutor` is the default
DEEP executor. `synthesis/model_hierarchy.json` configures the legacy `synth_king` pipeline the
product never launches. Two pipelines may legitimately run different rosters, so **equality was
the wrong assertion**. `README_PRODUCTION.md` had simply not been updated and is now projected
from the manifest by a generator. The hierarchy **declares its scope**, because
`sovereign_product` serves that file to the model as *evidence* and an operator asking "what
model is configured?" could be handed 8B while the product ran 3B. The gate enforces the
declaration and, decisively, that no file in `sovereign_product` resolves a role from the
hierarchy. The one equality control is replaced by **five** negative controls.

**R2.** `generate_build_manifest.py` enumerates **git-tracked** files, so untracked residue
cannot enter a release input, and is run deliberately rather than by a test.
`sync_release_manifest.py` re-pins derived hashes only after each artifact's own generator
vouches for it; a hand-authored file requires `--repin <path> --reason "<why>"`, one path at a
time, with the reason printed. The test now *verifies* instead of generating, and writes its
run-stamped copy to the gitignored `.runtime/` lane. **Running the suite now leaves the tree
clean.**

**CI.** The workflow provisions Python 3.12 *and* 3.14 and asserts both resolve through the `py`
launcher. `run_ci.ps1` builds the artifact from a named commit before the clean-room stage and
passes it explicitly. `Invoke-Script` runs child scripts as child processes so stage exit codes
are real. The gate list is the whole set — ten gates, up from five. The summary prints
**RELEASE-QUALIFYING** separately from the exit code and refuses to qualify when a
release-required stage was skipped, and warns at the top when the build commit differs from the
working checkout.

## 4. Workstream 3 — one operational contract

**Launchers.** One implementation, in `Start-Shell.ps1`, which supports both a source checkout
and an installed artifact and reports which it detected. `Start-Sovereign.ps1` and
`Sovereign Workspace.bat` are thin delegators that forward `-Port` / `-NoBrowser` / `-CheckOnly`
and propagate the exit code. Verified end to end through the `.bat`. Blocking and advisory
conditions are separated; `-CheckOnly` starts nothing and its exit code reports the blocking
result; readiness asks `/api/shell-info` for the shell's own identity rather than accepting any
listener; the caller's `GIT_OPTIONAL_LOCKS` is restored rather than deleted; `nvidia-smi` is read
per GPU and an unreadable census is reported as unknown rather than clean; the false light-mode
refusal claim is gone and the Windows theme is never modified.

While writing the test for this, a real bug was found in the delegation: splatting an **array**
binds positionally, so `@('-Port', $Port)` bound the string `-Port` to `[int] $Port`. Named
forwarding requires a hashtable splat.

**Dependencies.** README now states the 3.12/3.14 split and that both are required for an
install. `docs/SUPPORT-POLICY.md` already recorded the split; CI now matches it.

**State and docs.** SOW's normal-launch readiness receipt moved from
`<install>/modules/sow/.runtime/receipts` — a path `runtime_writes` declared nowhere, inside the
installation — to `${state_root}/receipts`. Writer (`main.js`), reader (`shell/modules/sow.json`),
the adapter compiler (`${state_root}` now resolves in `readiness.path` on the same containment
terms `runtime_writes` already used) and the tests all moved together. Three new tests assert
that the receipt is inside a declared write target and that no declared write target is inside
the installation.

README's stale P0-5 limitation is corrected with the historical record linked rather than erased;
`OPERATIONS.md` gains the launcher table with installation instructions for the two external
launchers, the offline snapshot contract, and the upgrade transaction's phases and exit codes;
`LIMITATIONS.md` records the closed lifecycle limitations accurately; `docs/RECOVERY-RUNBOOK.md`

## 5. Workstream 4 — acceptance

`docs/ACCEPTANCE-WORKFLOW.md` freezes one representative operator task with four independently
checkable artifacts and success criteria that do not ask the product whether it succeeded — a
SQLite integrity check and a byte comparison performed by a separate process, not a file count.
It states the recovery contract explicitly: what a crash may lose (a job still `running`, its
partial output), what it may not (a committed answer, its bytes, the database), and what would
never be acceptable.

It draws a hard line between two environments, and this report holds that line:

- **FIXTURE** — a temporary install on this development host. Proves the mechanism.
- **CLEAN** — a fresh Windows VM or clean host. The only thing that satisfies gate D.

`tools/acceptance/run_acceptance.ps1` executes the sequence and stamps the environment label into
every record. It refuses to run unless both the install root and the state root resolve under the
system temp directory, and refuses outright if the state root is the operator's real one, so it
cannot back up, restore over, upgrade or purge anything that matters. Steps that need a person at
the browser — the live workflow, and the cancellation and crash-checkpoint steps that depend on
it — are recorded **BLOCKED** with the reason rather than approximated: cancelling nothing proves
nothing.

`docs/RECOVERY-RUNBOOK.md` documents what to do when an upgrade, a backup, a restore, a launch or
a crash goes wrong, keyed to the exit codes the tooling actually returns.
